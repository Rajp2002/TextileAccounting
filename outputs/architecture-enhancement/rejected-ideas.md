# Rejected and deferred ideas

Reviewed: 2026-07-15 IST

“Rejected” means the repository shows no current value proportional to cost/risk. “Deferred” means a narrower version may become useful after a concrete trigger. Narola's proposal often names a sensible principle inside a technology choice; those are separated below.

| Proposal idea | Decision now | Why unnecessary/premature | Repository evidence | Future trigger that could justify reconsideration |
|---|---|---|---|---|
| Microservices | Rejected | Weavly is one product/team at pilot scale; splitting transactions and deployments would make production-stock-dispatch-payroll consistency harder and add network failure modes. | Core cross-domain transactions live effectively in PostgreSQL RPCs; one Next/Supabase deployment; no throughput/team ownership evidence requiring separation. | Sustained independently scaling workloads, clear team ownership, measured deploy coupling and a service boundary that does not break business transactions. |
| NestJS rewrite / separate backend deployment | Rejected | Existing Next server actions/routes plus Supabase RPC/RLS already provide server boundaries. A rewrite would recreate auth, tenancy, snapshots and 211 migrations with extreme regression risk. | `app/`, `lib/auth.ts`, `lib/supabase/*`, domain libs and transactional migrations; extensive current QA evidence. | A demonstrated platform limitation that cannot be fixed in-place, with funded migration/parallel-run and business reconciliation plan. |
| AWS, Azure or GCP migration merely for enterprise credibility | Rejected | Vercel + Supabase already provide hosting, PostgreSQL, Auth, Storage and Edge Functions. No availability, compliance, cost or performance evidence shows the platform is the blocker. | Vercel metadata, Supabase stack, current pilot ledger; real blockers are recovery proof, formula truth and terminology. | Contractual data residency/compliance, unavailable managed capability, sustained cost problem or measured reliability limit. |
| Kubernetes | Rejected | There are no containerized independently scaled services or an operations team to own clusters. It would add incident surface without product value. | Managed Vercel/Supabase topology; no container manifests or capacity incident evidence. | Multiple container workloads with measured scheduling/scaling needs and qualified operational ownership. |
| Containers as a deployment prerequisite | Rejected | Reproducible Node builds and managed deployment do not require containers at current stage. | `package.json`, Next/Vercel configuration, managed database/services. | A necessary self-hosted worker or regulatory deployment target that requires a container image. |
| Kafka, enterprise service bus or full queue platform | Rejected | Current asynchronous work is small: optional WhatsApp retries, webhooks and on-demand PDFs. Adding a broker creates ownership, ordering and recovery work. | Supabase Edge Functions, pg_cron retry, webhook event claims; no general backlog/throughput/failure data. | Multiple critical background workloads, persistent backlog, measured throughput/latency needs and an on-call owner. |
| Generic transactional outbox immediately | Deferred | The principle is valid, but current messaging is non-blocking and optional; payment webhooks already claim events. A provider-neutral schema with no current critical caller would be speculative. | `whatsapp_delivery_log`, retry cron, fail-closed modes, Razorpay claim state machine. | Live critical messages with unknown outcomes/duplicates or two-plus domains needing durable delivery. Start with a small DB outbox. |
| Redis as a system-wide cache/job system | Rejected | Upstash already serves narrow rate-limiting needs. General caching could introduce stale tenant/financial state and a new failure dependency. | `@upstash/redis`/ratelimit dependencies and `lib/rate-limit.ts`; PostgreSQL remains authoritative. | Measured hot read that cannot meet budget after query/index work, with explicit invalidation and fail-open/closed behavior. |
| Full event sourcing | Rejected | Audit logs, snapshots, movements and controlled reversals already retain consequential history. Replacing current relational state would multiply complexity and replay/migration risk. | Audit migrations, stock movements, production correction, payroll reversal, immutable quote/order snapshots. | Effectively none for current product; a future isolated ledger domain could use append-only records without system-wide event sourcing. |
| System-wide CQRS | Rejected | Read models/loaders and transactional commands can evolve within the modular monolith. A formal dual-model architecture would duplicate concepts without a measured bottleneck. | Existing route loaders/read models and SQL RPC commands. | A specific high-volume read model with measured write/read contention that cannot be addressed locally. |
| Native iOS/Android applications | Rejected now | Supervisor PWA already has mobile navigation, safe areas, draft recovery, install/update controls and weak-network handling. Native release/QA doubles operational scope. | PWA config, supervisor navigation/dashboard, OFF-009/OFF-010 evidence; physical install proof is optional BLOCKED, not a capability failure. | Required hardware/background/offline capability that browsers cannot provide, supported by pilot evidence and release ownership. |
| Broad visual redesign | Rejected | Owner and supervisor surfaces are role/task-oriented. Remaining UX gate is terminology validation, not aesthetics. | Owner sidebar/Factory Today, supervisor mobile source/tests/evidence, `UX-012`. | Repeated observed usability failures with task/time/error evidence. |
| Full ERP/general ledger/Tally replacement | Rejected | It materially expands statutory, tax, reconciliation and support liability beyond pilot scope. Narola itself excluded full statutory accounting from Option B. | `/owner/ledger` is archived; current commercials/payroll focus on operational truth. | Validated customer demand, accountant-approved rules, compliance ownership and separate acceptance scope. |
| Direct GST filing/government integration | Rejected | Requires regulatory expertise, evolving APIs and operational support not justified for limited pilot. | No active requirement; Narola excludes direct government integrations. | Qualified tax/legal scope, provider/API access, test environment and paying demand. |
| Broad yarn inventory module before pilot | Deferred | Source exists under an archived route; activation would expand scope and regression surface while the remaining recovery and estimator-truth gates are unfinished. | `/owner/inventory` archived by `lib/phase1-scope.ts`; estimator already snapshots yarn assumptions. | Pilot factories demonstrate a blocking yarn inward/issue/stock workflow and archived code passes fresh security/business QA. |
| Predictive analytics | Rejected now | There is no sufficient validated historical dataset, model objective, error tolerance or operator workflow. Predictions could mislead production decisions. | Narola conditions prediction on history; current performance/formula proof is more urgent. | Consented, clean multi-season data; defined decision, baseline and acceptable error; monitoring/owner. |
| Cross-factory benchmarking | Rejected now | Multi-tenant comparisons create privacy, consent, normalization and competitive sensitivity risks. | Strong tenant isolation is a current product property; no consent/aggregation model exists. | Explicit tenant consent, k-anonymity/privacy review, normalized metrics and proven customer value. |
| IoT loom integration | Rejected now | Hardware/protocol/installation/support details are unknown. It would create physical operational dependencies before the manual production flow completes first-shift proof. | No hardware API contract; `SIGNOFF-04` still awaits independent first-shift reconciliation; Narola conditions IoT on hardware details. | Named hardware/vendor API, pilot device, failure/manual fallback and funded field support. |
| Enterprise-priced monitoring/infrastructure budget | Rejected as a target | Narola's ₹35k-₹70k/month cloud plus monitoring/storage assumptions price a greenfield agency delivery, not repository need. Spend is not proof of readiness. | Managed current stack and low pilot scale; missing controls are mostly evidence/process and bounded commands. | Measured service limits, contractual SLA/compliance, or incident data demonstrating a paid tier/tool benefit. |
| Full platform-admin center | Deferred/narrowed | Existing admin code is broad, compliance-focused and archived. A cross-tenant portal raises service-role/security risk without demonstrated support volume. | `/admin` source and archive enforcement; current support can use controlled operational procedures. | Repeated support cases requiring tenant/subscription/provider lookup. Build read-first, audited, no default impersonation. |
| Unarchive public tracking immediately | Deferred | `/track` source exists but active routing archives it and share links were removed. Activating without re-running token/privacy/abuse QA would contradict current scope. | `lib/phase1-scope.ts`, `proxy.ts`, `/track/[token]` source and scope-doc inconsistency. | Buyer/owner demand plus current token expiry, rate-limit, variance and privacy acceptance. |
| General side-by-side estimator work before formula truth | Deferred | Four sensitivity scenarios already exist; broader comparison is useful only after real formula validation and pilot feedback. | `runScenarios`, Estimator UI, `GOLDEN-A-03` BLOCKED. | Repeated estimator-user need after formula acceptance; reuse one deterministic engine. |
| Rewrite working modules for uniform folder aesthetics | Rejected | File shape is a maintainability concern but does not itself improve pilot safety. Large changes would collide with active user work. | Dirty auth/performance campaign; large action/client files coexist with strong domain RPC boundaries. | Extract a bounded command when changing it for an evidenced defect, with callers/tests mapped. |

## Useful principles retained without literal technology adoption

| Narola principle | Smallest repository-fit interpretation |
|---|---|
| “NestJS domain services” | Clear command/read-model ownership in the existing Next.js modular monolith and transactional PostgreSQL RPCs. |
| “Queue-backed jobs” | Keep current database delivery log/cron; add a small transactional outbox only when live critical messages demonstrate need. |
| “Enterprise observability” | Extend Sentry/perf with safe operation IDs, structured fields and support codes. |
| “Cloud architecture” | Keep client-owned Supabase/Vercel accounts, explicit QA/production identity and lean CI/promotion controls. |
| “Platform administration” | A future audited, read-first tenant/subscription/diagnostic tool, not a broad portal or impersonation system. |
| “Immutable commercial history” | Preserve existing quote/order/rate snapshots and domain-specific movements/reversals. |
| “Mobile applications” | Continue the mobile-first Supervisor PWA until a proven browser limitation appears. |
| “Scale readiness” | Representative non-production data, query/route budgets and measured remediation before topology changes. |
