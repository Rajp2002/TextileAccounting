# Weavly idempotency matrix

Reviewed: 2026-07-15 IST

## Interpretation

This matrix separates duplicate-click protection in the browser from durable replay protection at the server/database boundary. A disabled button is useful UX, but it is not sufficient when a response is lost, a caller retries, two tabs submit concurrently, or an external provider replays a webhook. Verification status is limited to existing repository and runtime evidence; no database or live-environment mutation was performed for this review.

## Standard to adopt incrementally

Do not create a platform-wide framework first. For each new or repaired consequential command, apply this small contract:

1. The client creates one UUID when the operation begins and reuses it for retries until the outcome is reconciled.
2. The database stores the key under the authenticated organization with a unique partial index.
3. The transactional command checks the existing key before changing state and returns the original logical result on replay.
4. The same key with materially different input is rejected as a conflict.
5. The key is attached to safe Sentry/log context, not to sensitive payloads.
6. Tests cover concurrent duplicate calls, response loss/retry, cross-tenant key reuse, wrong-role denial, and refresh/re-login reconciliation.

This extends patterns Weavly already uses for quotes, sales, dispatches, receipts, billing, and webhooks. It does not require a universal idempotency table, Redis, Kafka, or a queue service.
