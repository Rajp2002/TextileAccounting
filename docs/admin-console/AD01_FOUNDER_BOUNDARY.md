# AD01 founder boundary

Development implementation on `codex/founder-admin`. No account, password, MFA
factor, founder grant, production setting, or hosted database was changed.

## Identity and data access

`getVerifiedIdentity()` validates Supabase `getUser`, the protected current
profile, and revocation. It permits a platform profile with no organization.
`getCachedSession()` remains the customer guard and rejects a missing organization.
The founder guard does not derive privileges from email, JWT role metadata, or
user metadata. An `admin` profile alone is insufficient.

Every founder request uses verified `getClaims`, checks subject, project issuer,
authenticated audience, expiry, immutable provider session UUID, and AAL2, then
calls the service-only session verifier. Its database joins the current enabled
UUID grant, non-revoked admin profile, `auth.sessions`, and the platform session.
Auth is not exposed as a Data API schema. The public fixed helpers return no
provider-session or private grant records. The single enabled grant constraint
prevents two active founders. There is no provisioning endpoint or seed grant.

An AAL1 candidate may only reach the challenge shell. Establishment after MFA
reads claims freshly rather than reusing a request-cached AAL1 result. In SQL,
establishment inserts once; conflicts never reset expiry or revive a revoked
session. Database server time enforces 15 minutes of interactive inactivity and
eight hours absolute duration. Read requests do not touch the activity time.
Only the explicit interactive endpoint may touch a still-valid session.

The existing global signout also revokes platform sessions before provider
signout. Revocation uses fresh provider identity and verified claims; it does not
depend on an available profile or an active grant. It reports whether matching
platform sessions were actually revoked. A cookie-bearing logout redirects only
after provider signout succeeds or platform revocation is confirmed; otherwise
it returns 503 for retry. Anonymous logout remains safe. Successful local logout
also clears all matching chunked Auth cookies. Revocation works while the feature
is disabled. Provider-session deletion independently denies token replay.
This is a shared same-origin Supabase identity: signout can end a customer session.
Logout POST requires an exact same-origin Origin; a present cross-site fetch hint
is denied. Browser fetch and native form submission supply this header. A missing
Origin does not bypass cookie-authenticated mutation protection.

## Gates and legacy contracts

`WEAVLY_ADMIN_ENABLED=true` is required for the new founder boundary. A production
build additionally requires `WEAVLY_ADMIN_PRODUCTION_APPROVED=true`. Both gates
must remain off until the identity, MFA/recovery, migration, reporting and release
approvals are complete. Neither flag bypasses authentication.

Role-only cross-factory RLS branches are retired. Existing tenant/public policies
remain. Legacy compliance actions independently call the new founder guard.
Legacy reads require `WEAVLY_ADMIN_LEGACY_READS_ENABLED=true` inside the server
guard as well as the page, so direct action calls cannot bypass the read gate.
Legacy writes and exports separately require
`WEAVLY_ADMIN_LEGACY_OPERATIONS_ENABLED=true`; external legacy lockdown delivery
requires `WEAVLY_ADMIN_LEGACY_DELIVERY_ENABLED=true`. All are off by default and
require the operational ownership decision before use. They are not MVP controls.
The old direct emergency-lockdown RPC and tenant-lockdown overloads are revoked.
Retained service-only isolation wrappers validate the exact founder session and
write safe audit in the same transaction. Source implementations remain private.

The migration was generated by the Supabase CLI as
`20261004092626_founder_admin_boundary.sql` and ordered after the AD00-reconciled
baseline as `20261004150000_founder_admin_boundary.sql`. It is additive to records;
it neither creates an organization for the founder nor alters customer access.

## Audit

Private audit records have no application update/delete grants. The shared SQL
append helper checks the founder session and permits only bounded scalar status,
category, priority, version, response-responsibility, due date and provenance
fields. Body text, raw requests, passwords and credentials are rejected. The
session is hashed. Read auditing fails closed. Support uses this helper inside
its own transaction. Denied attempts use a separate fixed-metadata helper,
bound to a verified provider identity and session; it confers no capability.

Nullable audit actors can be pseudonymized by a separately approved data-rights
process. Support/audit retention and deletion integration is a production gate;
no invented legal retention period, automatic purge or destructive cascade was
installed. Existing legacy mutations are compatibility operations, not a claim
that their complete historic data-rights/audit behavior has been redesigned.

## Approval and recovery runbook

1. Confirm the dedicated founder's existing Supabase Auth UUID with the owner.
   Never promote an account based on email or convert a customer owner silently.
2. In isolated staging, verify an admin profile without tenant organization,
   the one approved UUID grant, provider MFA factor, recovery procedure, and the
   negative identity/session/RPC tests. No enrollment or identity creation occurs
   through this console.
3. Obtain production approval for identity/security setup and each migration,
   backup/recovery point, support privacy retention/deletion integration and
   retained operational capability before applying changes.
4. Use the provider's supported MFA recovery flow with the verified account owner.
   If unavailable, keep the console disabled; never bypass AAL2 or tenant checks.
5. For emergency revocation through an approved secure database operation, set
   the exact UUID's founder grant `enabled=false, revoked_at=now()`, mark all of
   that UUID's platform sessions revoked, and sign out its provider sessions.
   Do not use a client endpoint or email lookup as proof of authorization.

Rollback first disables the new server gates, revokes affected platform/provider
sessions and grant if warranted, and restores safe application code. Keep
additive support/audit/reporting records. Do not restore role-only direct admin
policies, erase tickets or reverse payments. If schema correction is necessary,
use a reviewed forward migration rather than dropping populated private tables.
