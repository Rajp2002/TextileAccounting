# AD05 / AD06 support slice

Implemented additive migration `20261004150500_founder_support_workflow.sql`, support contracts/server DAL, `/api/support` and `/api/admin/support` routes, and requester/founder inbox and conversation screens. No account, production schema, real customer ticket, external message, or financial record was changed.

The migration was created with the Supabase CLI as `20261004092731` using `SUPABASE_TELEMETRY_DISABLED=1` (local telemetry writes otherwise exceed the sandbox). AD00's integration owner ordered it after the latest baseline and founder boundary at `20261004150500`.

Requester access uses current verified identity, current owner role, valid organization, and revocation checks. Paid entitlement and business lockdown do not gate this dedicated support path. Reads require the requester UUID; a peer in the same organization cannot read the conversation. Customer responses are projected without internal references, notes, or internal actions. All direct client table access/mutations are revoked; exposed RPCs are service-role-only, with fresh owner/founder SQL checks. Private notes and idempotency records live in the private schema.

Mutations lock the ticket, append monotonic message sequences, update response responsibility/state, write immutable timeline and required founder audit, and commit together. The validated JSON payload's canonical SHA-256 and immutable actor UUID key enforce retries. Original successful results precede version checks. Founder initial manual intake does not count as a public human response. Internal notes cannot clear reply responsibility or fulfill promises. Bound public resolutions require a committed public summary; unbound manual resolutions are private. Customer replies reopen resolved/waiting tickets. Status changes and promise fulfillment/replacement have separate safe history.

Founder lists prioritize critical, overdue, needs-reply and waiting-fix work before other requests, then stable timestamp/UUID order. Cursors include priority rank and snapshot time. Detail output is bounded to 200 messages/events/notes per page, with separate safe cursors and explicit older-history controls. Private-note cursors are founder-only.

Public sends have an immutable in-memory request key/payload until confirmed success or a definite validation/conflict rejection (400/409). A lost response followed by ticket refresh reuses the original version and key; it cannot allocate a second key silently. Unconfirmed attempts freeze editing and provide an exact retry. Drafts and attempts are not persisted. Separate “Send to customer” and “Add internal note” actions have no Enter shortcut. Replies are explicitly in-app.

Verification is synthetic/local only. Named suites are `__tests__/admin-support.test.ts`, `__tests__/admin-support-send-attempt.test.ts`, and `__tests__/db/admin-support.dbtest.ts`. The DB suite includes1,000synthetic organizations/5,000tickets and10samples against a1,000ms p95 local list budget. Actual measurements are saved to `/tmp/weavly-support-performance.json` by the test for release evidence. The DB suite uses the repository's disposable loopback PostgreSQL harness, including a simultaneous customer-reply/founder-resolution race, concurrent identical retries, private-note/peer/tenant isolation, current revocation, direct Data API denial, and audit failure rollback. Sandbox shared-memory denial required an approved local-only escalation for `initdb`; no hosted DB was used. Final integrated lint/typecheck/build/browser results are recorded by the integration owner.

Release gates remain: approved production support retention/deletion integration, recovery/contact owner, founder identity/MFA, and explicit production migrations/deployment. Existing organization deletion must consider retained tickets; no automatic purge or new retention period was invented. Actor/requester UUID foreign keys can pseudonymize on Auth-user deletion; stable textual idempotency actor keys survive. Production support requires both `WEAVLY_SUPPORT_ENABLED=true` and `WEAVLY_SUPPORT_PRODUCTION_APPROVED=true`; founder paths also require the founder gates and session boundary.

Rollback: disable support server gates first, retain tickets/messages/notes/events and audit data, and use the current published contact/recovery route. Do not drop populated tables or restore generic-admin access. Additive forward corrections are required after records exist. New private notes are never redirected into an external/public channel.
