# Founder email and first-TOTP setup follow-up

This development slice implements the approved email/password first factor and
first-TOTP enrollment contract. No real identity, grant, password, MFA factor,
security setting, or hosted database has been changed. Provider enrollment and
production enforcement remain separately gated. The approved email is a guard
condition, never a self-service grant or a substitute for the approved Auth UUID.

## Protected email binding

Migration `20261004154000_founder_email_and_mfa_setup.sql` was generated by the
Supabase CLI as `20261004105024_founder_email_and_mfa_setup.sql`, then ordered
after the existing additive migration dependencies. It adds the canonical
`private.platform_founder_grants.login_email`, defaulting to the approved
`rajpatel86420@gmail.com`. It inserts no grant or user. Test grants explicitly
bind synthetic `example.test` emails; real customer data is not used as fixtures.

Candidate, platform-session, and privileged SQL checks independently join the
current Auth UUID, enabled/non-revoked grant, admin/non-revoked profile, live
provider session, and current confirmed Auth email. Email comparison trims and
lowercases the current provider email against the protected canonical value.
An old profile email, JWT metadata, or the same address on another UUID cannot
confer access. Email changes fail closed until a protected update is approved.
The revoke operation stays usable after grant, email, or profile changes because
revoking access does not require retaining privilege.

## Narrow setup RPC

`public.admin_founder_mfa_setup(p_user_id uuid, p_session_id uuid,
p_operation text, p_factor_id uuid DEFAULT NULL, p_intent_id uuid DEFAULT NULL,
p_verification_id uuid DEFAULT NULL)` is service-role-only. Request actors and
session IDs are derived from the verified candidate by server code. Its private
intent storage has no client or service-role table grants. Auth schemas remain
outside the exposed Data API.

The successful response is `{ allowed: true, intentId, factorId, status,
expiresAt }`. `factorId` is null before binding. `verify` additionally returns
`verificationId`; `restart` may return `abandonedFactorId`. No OTP, secret, QR,
password, enrollment URI, provider payload, or customer record is stored or
returned by this RPC. Denials return `{ allowed: false, code,
retryAfterSeconds? }`; invalid operations raise a bounded argument error.

| Operation | Required state and effect |
| --- | --- |
| `begin` | AAL1, approved candidate, and no verified provider factor. Creates one per-user enrollment intent with a 30-second lease and 10-minute lifetime. Concurrent/active attempts are denied. |
| `bind` | Same session and intent; active enrollment lease; actual owned unverified TOTP factor. Binds provider factor metadata, with idempotent same-factor retry. |
| `status` | Same candidate session; returns only bounded setup metadata. It does not expose another session's intent. |
| `verify` | Same pending intent and actual unverified TOTP factor. Acquires a 30-second lease with a new verification UUID. An active verification lease blocks another attempt. |
| `verify_failed` | Same session, intent, factor, and current verification UUID; still AAL1/unverified. Releases the lease only after an explicit provider invalid-code result. A delayed response cannot clear a newer lease. |
| `complete` | Same session, intent, and factor; actual provider AAL2, matching `auth.sessions.factor_id`, and owned verified TOTP. Records completion without granting a platform session. Retry is safe. |
| `restart` | Explicit same session and current intent, after its active lease expires; no verified provider factor. Issues a new intent UUID, invalidating stale callbacks. Only an owned unverified factor ID may be returned for reviewed cleanup. SQL never removes a factor. |
| `abandon` | Same intent and session; no active verification lease or completed intent. Marks metadata abandoned without touching provider factors. |

Operations serialize with a per-user transaction lock. Setup metadata and the
safe state-only audit commit together; audit failure rolls the metadata back.
Any business/admin data still requires AAL2 plus a valid platform session.
Completion relies on authoritative provider state rather than the verification
lease UUID, allowing recovery from a lost successful provider response.

The server checks provider factors freshly before enrollment and never calls
`unenroll`. Interrupted unverified factors are retained for approved recovery.
A delayed verification can change a provider snapshot between calls, so
automatic factor cleanup cannot safely promise to preserve verified factors.
If pending factors exhaust the provider limit, setup fails closed and requires
recovery. Network uncertainty leaves the
30-second verification lease intact. A user-provided code, client assurance claim,
QR image, or local intent status cannot establish AAL2.

## Verification and limitations

The disposable DB harness models the current Auth `sessions` columns `aal` and
`factor_id`, and the factor table's ID/user/type/status metadata. The current
[Auth session model](https://github.com/supabase/auth/blob/master/internal/models/sessions.go)
and [factor model](https://github.com/supabase/auth/blob/master/internal/models/factor.go)
were checked against provider source. This verifies SQL boundaries and synthetic
state transitions, not live provider MFA behavior or deployed schema.

Named DB tests cover fresh confirmed email, UUID authority, provider-session
binding, concurrent begin, factor ownership/type/state, no verified-factor
replacement, explicit restart, stale intent/verification responses, actual
AAL2 completion, expiry, direct API/private-table denial, safe audit and audit
rollback. Existing founder/factory/support/payment fixtures use explicit
synthetic email bindings to verify the integrated guard.

Focused validation: **12/12 new MFA database tests passed** in the disposable
database; **37/37 existing founder/factory/payment/support tests passed** in the
integrated replay. Targeted lint passed with zero warnings. Two initial synthetic
fixtures were corrected to respect the exact lifetime and enabled/revoked grant
constraints. These counts are local development evidence, not production proof.

Production setup still needs the approved UUID, applied-schema review, provider
enrollment/recovery verification, security approval, and production gates.
The UI may return a QR PNG only to the verified candidate in memory; it must
not persist that image or enrollment URI in storage, caches, replay, logs, or
telemetry. Setup metadata retains no credential. Its retention/deletion policy
requires operational review; no automatic purge or invented legal period is
installed here.

Rollback disables enrollment and founder server gates first. Preserve audit and
additive metadata; revoke affected platform/provider sessions through the
approved secure flow when warranted. Never recover access by removing the
email/UUID/MFA checks or restoring role-only admin authorization. A populated
schema is corrected through a reviewed forward migration.
